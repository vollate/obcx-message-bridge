## Context

`CommandRoutingTable::render_help` currently calls `permits` for each bot catalog entry. `CommandCoordinator::process` uses the same ACL evaluator before dispatch, but neither sees actor configuration. Bridge subsequently resolves the source installation and group/topic mapping inside `BridgeForwardingRuntime::handle_command`; ExHentai checks an exact configured destination inside `authorized_destination`. These later checks explain why a command can be ACL-permitted yet unusable in the source group.

Generation construction already discovers data-only command contracts before actor construction, then calls `prepare_generation` with a generation-local service/configuration view. Bridge and ExHentai parse immutable configuration there, including in validation-only mode. This is the appropriate place to derive command scopes without invoking a command handler or introducing a new dynamic-library export.

The existing coordinator runs configured message observers before detection and authorization. This change does not reorder that phase. References below to no command side effects mean no additional command handler, command-triggered provider operation, or ordinary fallback pipeline; they do not promise to undo existing message observation.

## Goals / Non-Goals

**Goals:**

- Derive availability automatically from the actor's authoritative parsed configuration, with no duplicate operator-maintained group list.
- Use one core eligibility path for help and command dispatch: exact active route AND effective ACL AND actor scope.
- Preserve exact installation identity, Telegram topic distinctions, reload ownership, and validation-only safety.
- Integrate all Bridge canonical commands and ExHentai, and provide an installed-SDK extension for other actors.
- Distinguish an explicitly empty scope (nowhere available) from missing required publication (invalid candidate).

**Non-Goals:**

- Predict successful argument parsing, reply-message availability, manager-only subcommand authorization, connectivity, quotas, or other transient execution conditions.
- Filter Telegram's bot-wide command menu per caller or publish per-chat menus.
- Add arbitrary actor callbacks, handler probes, HTTP/DB queries, scripts, or a general authorization expression language to help evaluation.
- Change actor configuration defaults, ACL override semantics, bridge forwarding direction semantics, persistent storage, or unrelated actors.

## Decisions

### 1. Publish data-only scopes rather than invoking actor predicates

Extend command observation metadata with an explicit `availability = "actor_scope"` marker generated by an SDK declaration. Absence preserves the existing ACL-only protocol for old and non-participating actors; it is not a new TOML configuration option. Unknown marker values and malformed metadata are rejected. New actors using the marker require a supporting core; no new V2 export or interface virtual function is introduced.

An installed SDK service provides an actor-scoped preparation-time publisher. A marked command publishes a finite immutable set of allowed contexts derived from the same parsed config used by its handler. The initial context model contains:

- normalized platform and exact installation id;
- exact native group id;
- an explicit topic selector: no topic, one positive Telegram topic id, or any topic including no topic.

Scopes represent group conversations only in this slice. Private callers cannot match these scopes. An explicit empty set is valid and denies every caller. There are no wildcard installations/groups and no sender lists: caller ACLs remain responsible for user access. QQ scopes must use the no-topic selector.

The publisher binds ownership to the actor's preparation context. It accepts only that actor's marked canonical commands, rejects duplicate publication and malformed scope records, and cannot replace another actor's publication. Equivalent scope values can be canonicalized/deduplicated; unknown or disabled installations and platform/type mismatches fail candidate validation. Actors may publish declared commands that have no active route; only active routes contribute to help and dispatch.

The frozen table owns copied value data, not actor objects, function pointers, or plugin-owned deleters. This avoids introducing a dynamic-library lifetime hazard into help. Core understands only generic identity/topic matching, never Bridge or ExHentai TOML field names.

**Alternatives rejected:** manual ACL overrides duplicate group configuration; teaching core to parse individual actors couples layers; calling a handler with a dry-run flag risks side effects; registering arbitrary predicates adds executable lifetime/concurrency/error handling when static configuration scopes suffice.

### 2. Finalize availability after preparation and before publishing routes

Split command generation construction into structural validation and final availability binding:

1. Discover contracts and validate configured routes, ACLs, bot capabilities, and complete help bounds as today.
2. Create a generation-local availability builder and supply an owner-bound publisher during each actor's existing preparation hook.
3. Actors derive scopes immediately from validated parsed config, including before validation-only early returns. Scope generation does not initialize workers, mutate storage, or require provider I/O.
4. Finalize a new immutable command table using the candidate's own scopes. Every active marked command must have published a scope, even when empty. Missing publication rejects the candidate, never silently permits or merely hides the command.
5. Publish the coordinator/generation only after finalization succeeds. Reject all subsequent attempts to modify the frozen scope state.

The existing actor-specific preparation work is otherwise retained; this feature adds no new preparation I/O. Validation-only follows the same scope derivation and validation path. Failed reload candidates cannot mutate active scopes. Old admissions retain the old table and new admissions use the new table only after successful cutover.

### 3. Use one eligibility result in both consumers

Introduce one route-aware eligibility operation with stable outcomes: eligible, ACL denied, actor unavailable, and no active route. Reuse the trusted normalized subject extraction already required for ACLs; validate identity before scope matching. The canonical route name is used after exact/RE2 selection, so aliases cannot bypass availability. No second route or actor is tried after an unavailable match.

For help, evaluate the canonical entries for the exact source bot, include only eligible actor commands, and preserve existing order, descriptions, UTF-8 bounds, and pagination. Reserved `help` remains core-owned and ACL-controlled, with no actor scope. Thus an authorized caller with no available actor commands still gets `/help`.

For execution, evaluate eligibility before constructing the command transaction or scheduling its handler. ACL denial keeps `command_access_denied`; an ACL-permitted but out-of-scope invocation terminates as `command_unavailable` and is consumed without a chat reply. It does not use the route's transaction-error fallback. Truly unmatched commands, valid handler completions, transaction failures, and the pre-command observer phase retain existing behavior.

Diagnostics use stable codes plus generation/actor/command/installation metadata. They do not dump scopes, native group/user ids, source payloads, arguments, or configuration secrets.

**Alternative rejected:** hiding only in help leaves the actual dispatch boundary inconsistent. Treating an unavailable recognized command as unmatched or falling back to ordinary pipelines could still trigger unrelated actor processing; the proposed behavior mirrors existing ACL denial.

### 4. Bridge derives scopes from its existing source-route semantics

Bridge marks `bridge_status`, `recall`, and `poke` as actor-scoped. Extract a pure command source-resolution/projection helper around the existing pair and mapping logic; use that helper to generate scopes and retain matching defensive checks in execution. Do not create a second hand-written group list.

- Select pairs by exact source installation; equal native ids in another pair never match.
- QQ exposes only `bridge_status`, for sources resolvable by the existing `tg_group_and_topic_id` behavior, including its `enable_qq_to_tg` conditions.
- Telegram exposes the three commands where the current group/topic route resolver finds a QQ destination. A group-to-group mapping permits any topic as the current handler does; a topic-to-group mapping permits only its configured positive topics.
- Preserve current Telegram command direction behavior rather than adding a new forward-direction restriction. Command availability is not identical to whether ordinary forwarding is enabled.
- No mapping, unsupported platform/command, or private conversation produces no matching scope.

The same generic scope matcher is available to actor-side guards; target resolution remains Bridge-owned and uses the same parsed config and pure route helpers. Tests compare scope projection and resolution, including disabled directions, so the two paths cannot drift unnoticed.

### 5. ExHentai derives scopes from exact configured destinations

ExHentai marks `exhentai` as actor-scoped and projects its parsed Telegram/OneBot target collections into exact installation/group/topic scopes. A configured Telegram destination without a topic matches only the no-topic context; a configured positive topic matches exactly that topic, consistent with `ExHentaiConfig::destination`.

Refactor destination normalization/lookup so availability and `authorized_destination` use the same trusted identity model and configuration-derived matching. Keep source-envelope consistency checks for direct actor requests; never derive availability from command arguments or an untrusted raw provider field. Regression tests cover contradictory raw versus normalized topic identity.

`manager_ids` continue to gate mutation subcommands inside `authorize_command`. An ordinary user in a configured destination can still search/read, so an empty manager list does not hide the canonical `/exhentai` command. Syntax checks and transient service failures likewise do not influence help visibility.

### 6. Keep compatibility and platform menus explicit

Existing actor registrations without the marker keep ACL-only availability. Bridge and ExHentai require scope publication after their declaration changes; testing must not mask a missing publisher in production with an unrestricted result. Standalone handler unit tests may inject explicit scope fixtures, while installed-SDK integration tests exercise real preparation and finalization.

The aggregate platform catalog remains the complete active canonical catalog, including commands unavailable to a particular caller. Only the textual `/help` reply becomes actor-scope-aware. Documentation must explain this distinction so Telegram's command suggestions are not mistaken for a remaining help bug.

## Risks / Trade-offs

- **[Availability changes source propagation]** → Document that recognized unavailable commands are consumed, test both configured fallback modes, and preserve pre-command observers and genuinely unmatched traffic.
- **[Scope projection drifts from actor execution]** → Extract shared pure source/destination helpers, use the common matcher, and add parity tests over installations, topics, and direction flags rather than reproducing actor configuration rules in core.
- **[Generation build ordering accidentally permits missing scopes]** → Keep structural validation separate from final readiness, reject missing publications, and exercise startup/validation-only/reload paths.
- **[Large configs duplicate scope memory]** → Canonicalize and index immutable value sets, share equivalent per-actor sets where practical, and perform no per-message config parsing or unbounded external work.
- **[Legacy actors still expose commands beyond their internal scope]** → Preserve compatibility explicitly; migrate other actors separately through the same opt-in SDK API rather than inventing scopes for them.
- **[Help cannot promise successful execution]** → Document the distinction between configuration eligibility and invocation-specific authorization/validation, especially manager operations and reply-based Bridge commands.

## Migration Plan

1. Implement SDK metadata, data-only scope publication, generation finalization, and the common eligibility operation with fixtures first.
2. Migrate Bridge and ExHentai from their existing parsed configurations, add parity and cross-actor integration tests, and update SDK install/surface tests and operator docs.
3. Build and test core plus affected actor repositories with at least six workers (all available cores when load is low). Use synthetic configuration and mock providers; do not invoke live bots or mutate deployment configuration/databases.
4. Deploy the supporting core and rebuilt actors together, run `--validate-config`, then activate through the existing reload/restart workflow. Existing ACLs remain additional restrictions and require no edit.
5. Verify that a synthetic equivalent of QQ `1004979108` shows `/exhentai` and `/help` but not `/bridge_status`, and that manual `/bridge_status` submission dispatches no command handler.
6. Roll back by restoring the preceding compatible core/actor bundle. No storage rollback is needed; the previous help visibility and fallback behavior return.

## Open Questions

None blocking the proposal. This design intentionally uses consume-on-unavailable, limits actor scopes to configuration-derived group/topic contexts, and leaves invocation-specific permissions in handlers; any expansion should be made explicitly before implementation.
